# Render deployment

The root Dockerfile builds React and runs Nginx with one threaded Gunicorn
worker. Nginx serves the frontend and proxies API and Socket.IO requests over
loopback. Deploy one instance: realtime rooms currently live in that process.

## External services

- Use a separate `matcha` database and `matcha_app` role in the existing Neon
  project. `DATABASE_URL` must be a direct PostgreSQL connection string with SSL.
- Use the private `matcha-photos` R2 bucket. Create an R2 S3 API token with Object
  Read & Write permission scoped to this bucket. Set `S3_REGION=auto` and the
  account's S3 endpoint. Keep `S3_CREATE_BUCKET=false`.
- Use Brevo SMTP with STARTTLS on port **2525**. Render free services block the
  usual SMTP ports 25, 465, and 587. Use a Brevo SMTP key and the SMTP login, and
  an accepted sender address. No Brevo API key is needed.

Production secrets are stored locally in `.env.production`, which Git and the
root Docker build exclude. The file uses shell quoting; Docker's `--env-file`
does not interpret that quoting. Use Docker Compose or a dotenv-aware loader
when testing locally. Never use the shared instance owner's credentials as the
application's database login.

## Create the Render service

1. Push the root `Dockerfile`, `.dockerignore`, `deploy/`, and `render.yaml` to
   the GitHub repository before creating the service.
2. In Render, create a Blueprint from the repository and use `render.yaml`.
   Alternatively, create a Docker web service named `matcha` with the repository
   root as its build context and `./Dockerfile` as its Dockerfile.
3. Select Ohio to match the existing Neon compute, one instance, and the free
   plan. Set `/api/v1/health` as its health check.
4. Supply the secret environment variables requested by the Blueprint from
   `.env.production`. `OAUTH_STATE_SECRET` is generated by the Blueprint; if
   creating the service manually, supply the local production value.
5. Set `VITE_MAPBOX_ACCESS_TOKEN` before building. This is a public browser token
   embedded into the frontend. Changing it requires rebuilding the image.

At startup the container applies database migrations, verifies R2 access, and
starts the two app processes. No persistent Render disk or Render database is
needed. The app uses Render's `RENDER_EXTERNAL_URL` as `APP_ORIGIN` unless an
explicit `APP_ORIGIN` is set. For a custom domain, set its full HTTPS origin.

Optional social login needs production provider credentials and callback URLs:

```text
https://<app-host>/api/v1/auth/google/callback
https://<app-host>/api/v1/auth/github/callback
```

## Verify the deployment

- `/` returns the frontend, and a client-side route also serves the app.
- `/api/v1/health` returns `{"status":"ok"}` through Nginx and Neon.
- Socket.IO polling and WebSocket upgrade both work through `/socket.io/`.
- Signup verification, password reset, and email change links use the public
  HTTPS origin and arrive through Brevo.
- Photo upload, read, and deletion work against the private R2 bucket.
- Login cookies are secure and chat reconnects after a service restart.

Do not run the demo seed command in production. Existing local database records
and objects are not copied automatically.
